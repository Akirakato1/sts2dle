# Game Guidance, Codex Data Fidelity, Sprite Readiness, and Guess Ordering

## Goal

Make STS-dle self-explanatory and eliminate four sources of first-use confusion:

1. Explain the green, yellow, and red comparison results and the paired base/upgrade rules.
2. Preserve Spire Codex card-type and rarity values instead of collapsing valid source values.
3. Ensure both sprite atlases are loaded and decoded before the player can search or guess.
4. Display the newest guess at the top of the result rows without changing stored history order.

## Rules and Legend UI

The game panel will show an always-visible color legend below the Daily/Practice controls. It will use color swatches plus text so meaning never depends on color alone:

- **Green:** both the base and upgraded features match.
- **Yellow:** exactly one of the base or upgraded features matches.
- **Red:** neither version matches.

An adjacent compact `How to play` disclosure will be collapsed by default and use native accessible disclosure semantics. Its content will explain:

- The player guesses a base card name.
- Each tile compares the guessed base card to the answer's base card and the guessed upgraded card to the answer's upgraded card.
- Keyword tiles use X and checkmark icons to show whether a keyword is absent or present in the base and upgraded card.
- Cards with identical complete paired feature sets are accepted as equivalent answers.
- Daily uses the UTC date, restores its progress, and produces a share result after a win.
- Practice creates unlimited random rounds and does not produce a share result.

The existing brief paired-comparison note will be removed or folded into the expanded rules so the page does not repeat itself. The legend and disclosure must fit without widening the 1280 px shell or changing the guess grid's owned horizontal scrolling behavior.

## Keyword Existence Icons

Keyword tiles will use decorative inline SVG icons instead of blank cells or text glyphs:

- X icon: absent in both the base and upgraded card.
- Checkmark icon: present in both the base and upgraded card.
- X icon, right arrow, checkmark icon: absent in the base card and gained on upgrade.
- Checkmark icon, right arrow, X icon: present in the base card and lost on upgrade.

The icons describe the guessed card's base/upgrade state. The tile's green, yellow, or red background independently describes whether that state matches the answer. The X and checkmark use a shared small icon component with `currentColor` strokes; no icon-library dependency is added. Icons and the visual arrow are hidden from accessibility APIs because the tile's existing accessible label will continue to say `absent`, `present`, `absent to present`, or `present to absent`, followed by the comparison result color.

## Spire Codex Feature Domains

### Card type

Use the stable English `type_key` supplied by Spire Codex as the canonical public feature value. The current accepted domain is:

- `Attack`
- `Skill`
- `Power`
- `Quest`
- `Status`
- `Curse`

Do not independently remap these values. Source-schema parsing and snapshot validation will reject an unknown type instead of silently converting it.

### Rarity

Use the stable English `rarity_key` supplied by Spire Codex as the canonical public feature value. The current accepted domain is:

- `Ancient`
- `Basic`
- `Common`
- `Curse`
- `Event`
- `Quest`
- `Rare`
- `Status`
- `Token`
- `Uncommon`

No current card has a null rarity. Unknown or missing rarity is an invalid source/snapshot condition; it must not be collapsed to `None`. Falling Star therefore has rarity `Basic` in both its base and upgraded feature vectors.

### Card class

Spire Codex supplies a structural `color` identifier rather than the desired player-facing class grouping. Keep the intentional seven-class mapping:

- `ironclad` -> `Ironclad`
- `silent` -> `Silent`
- `defect` -> `Defect`
- `necrobinder` -> `Necrobinder`
- `regent` -> `Regent`
- `event` -> `Event`
- `colorless`, `token`, `quest`, `status`, and `curse` -> `Neutral`

This is the only class transformation. It prevents Class from duplicating Type and Rarity for special neutral cards.

### Snapshot and group consequences

The shared TypeScript domain, client schema, server validator, fixtures, and tests will use the complete canonical type/rarity domains. The snapshot format is strict, so stale snapshots that contain the old collapsed rarity values are rejected and rebuilt on normal synchronized startup.

Feature keys and base/pair groups continue to be generated by the existing ordinary `FEATURE_ORDER` serialization. Rebuilding with the corrected rarity values will naturally split or combine groups as required; there is no migration or post-processing merge pass.

Because Daily identity includes the source revision and ruleset, the Daily ruleset version must advance when this feature-domain correction lands. Existing statistics remain under their current independent stats key.

## Sprite Atlas Readiness

The current client loads sprite-map metadata but does not request either WebP atlas until a visible CSS background first references it. The candidate atlas is currently about 676 KB and the guess atlas about 3.2 MB, which causes visible first-search and first-guess delay.

After runtime JSON has been fetched and strictly parsed, snapshot loading will preload and decode both `spriteMap.candidate.url` and `spriteMap.guess.url` before resolving the loaded snapshot. The two atlas operations run concurrently.

The preload utility will:

- create one image request per distinct atlas URL;
- wait for successful image load and decode;
- treat load or decode failure as snapshot-load failure;
- observe the existing startup `AbortSignal`, remove listeners, cancel pending image work where supported, and never surface cleanup aborts as user-facing errors;
- use sanitized fixed error messages that do not echo attacker-controlled URLs;
- support environments without `HTMLImageElement.decode()` by accepting a successful load event.

The application remains in its existing loading state until both atlases are ready. A preload failure uses the existing load-error panel and `Try again` action. This intentionally prioritizes guaranteed instant first interaction over displaying the game before its sprite resources are usable.

Preloading the exact URLs later used by CSS allows the browser's same-document memory cache to satisfy candidate and guess-row rendering without a second first-use transfer.

## Newest-First Guess Rows

The reducer, persisted Daily representation, share generation, and submitted-guess list remain chronological from oldest to newest. Only `GuessGrid` presentation reverses the rows.

The rendering layer will derive a newest-first view while retaining each guess's original chronological index and stable identity. That original index remains the basis for:

- deciding whether a restored row is immediate or animated;
- identifying the one newly submitted row that should reveal;
- reveal completion and timeout ownership;
- stable React keys.

This means a new guess appears directly below the header and reveals there, while older settled guesses move downward without replaying animation. Restored Daily guesses render newest-first and immediately. Share symbols and stored histories remain in original guess order.

## Error Handling and Accessibility

- Legend entries include visible text in addition to swatches.
- The rules disclosure has an accessible name and keyboard-native toggle behavior.
- Keyword X/checkmark icons never replace the explicit accessible keyword-state label.
- Atlas failures reuse the existing retry surface and do not leave an interactive game with missing sprite assets.
- Unknown Codex type/rarity values fail closed during synchronization and validation.
- No source URL or filesystem payload is added to user-facing preload errors.

## Testing and Acceptance

Automated coverage will prove:

- the visible legend contains all three exact meanings without relying on color alone;
- the `How to play` disclosure exposes all game rules and works by mouse and keyboard through native semantics;
- keyword tiles render inline SVG X/checkmark icons for stable absence/presence and both upgrade directions while retaining explicit accessible state text;
- all current Codex type and rarity values pass through canonically;
- unknown/missing type or rarity values are rejected;
- Falling Star normalizes and renders with rarity `Basic`;
- strict client/server snapshot schemas reject the old collapsed domain;
- feature groups are recomputed from the corrected vectors without a merge path;
- candidate and guess atlases begin together, each preload once, and snapshot loading resolves only after both are decoded;
- abort, load failure, decode failure, duplicate atlas URL, and no-`decode` fallback behavior are deterministic and cleanup-safe;
- newest guesses render first, restored rows remain immediate, only the new row animates, and reveal completion cannot unlock early or stall;
- persistence and Daily share order remain chronological;
- 390 px, 768 px, and 1440 px browser tests retain document overflow guarantees and the grid owns any necessary horizontal scrolling;
- browser acceptance makes no live Spire Codex request and verifies the first candidate and first submitted row have already-complete sprite atlas resources.

After unit, type, build, and offline browser verification, a fresh live synchronized snapshot will be built in a disposable writable directory. Acceptance will record card/group counts, verify Falling Star is `Basic`, confirm every runtime type/rarity is in the Codex domain, and confirm both atlas requests complete before gameplay becomes interactive.

## Out of Scope

- Changing the ten feature columns or comparison colors.
- Changing answer selection or equivalence rules.
- Reordering stored guesses or share symbols.
- Adding directional mana hints or correctness result marks; keyword-state X/checkmark icons are not correctness marks.
- Passing Codex structural colors through as eleven player-facing classes.
- Preloading all full-card CDN images; only the two local sprite atlases are startup-blocking.
